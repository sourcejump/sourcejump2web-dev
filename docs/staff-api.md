# Staff API
What the endpoints behind the staff tools do. Staff act on the pages the tools are about (a run's page, a player's or map's Manage view, `/servers`, `/community`); the `/staff` area keeps the log and API keys. Shared rules are in `api.md`, the rest of the website's endpoints in `site-api.md`.

- Everything under `/v1/staff/` takes `Staff` (`staff/access.rs`): a session whose player holds a staff privilege (any but `post_community`), and our `Origin` for anything but a read. Each route then requires its own privilege. On the web, the `/staff` sidebar never gates a page; each page's own read says why it's refused.
- `GET /v1/staff/keys`, `POST /v1/staff/keys` (new server, or a new key replacing its old one; shown in that response only), `POST …/keys/{prefix}/revoke` (with a reason) need `manage_keys`. `GET /v1/staff/servers` (each server as the public list shows it, plus its report and listing) `PUT`/`DELETE /v1/staff/listings/{ip:port}`, and `PUT`/`DELETE …/listings/{ip:port}/whitelist` (mark a listed server as whitelist or public; `404` when it isn't listed, and unlisting drops the mark) need `manage_servers`.
- `GET /v1/staff/maps?q=` lists every map, including ones with zones and no runs (`no_runs=true` for only those, the Maps page's staff tab); `GET /v1/staff/maps/{map}` answers for any valid name, so zones can be set up before a map's first run; it carries the map's `viewer_file` for the zone editor. `PUT …/tiers/{track}`, `PUT …/description`, `PUT …/release` (`released`: a year, month or day, not in the future; `mapper` as any SteamID form) and the pictures (`staff/map_images.rs`: `POST …/images` with the picture as the body, `DELETE …/images/{id}`, `PUT …/images/order` naming every picture once, `PUT …/images/{id}/focus`) need `manage_maps`; a map's picture changes lock its row, so two uploads can't both take the 10th place; the CLI's `maps import-pictures <folder> <note>` gives maps without pictures their first ones from one folder per map (`<map>/` or `<map>/screenshots/`), encoding on the machine running it so only the WebP files are uploaded, the owner's `<map>_owner_*` shot first as the cover, too-small shots left out rather than scaled up, one log entry per map (`--dry-run` reports only); `POST …/zones` (whole set, `based_on`, note) needs `manage_zones`. The viewer file (`staff/map_viewer_file.rs`) takes either privilege, since zoning needs the file, and uploads in two steps, because Cloudflare refuses request bodies over 100 MB on the way to the API: `POST …/viewer-file/uploads` gives a 15-minute presigned link into the private staging bucket (`storage::Staging`, never served), the page uploads the packed map there (brotli, up to 256 MB), then `PUT …/viewer-file` names the upload; `GET /v1/staff/viewer-files` lists every stored file's map, hash and size, for the Maps page's bulk upload, and as `missing` the maps with valid runs and no file, most stored replays first, which the tab lists below the upload. The API reads it (stopping past 256 MB), checks it by stripping it again, which must change nothing, and stores the bytes it checked; it adds a map SourceJump hasn't seen and replaces the old file. Packing happens in the page because brotli at quality 11 takes minutes of CPU on a large map (3–4 s per MB in WebAssembly); the packer is `api/crates/viewer-pack-web`, built into `web/public/viewer-pack.wasm` by `just wasm` and committed. For many maps at once staff run `sj-pack`, the same packer natively, several maps in parallel; it and the packer live in the public `sourcejump-packer` repo, whose GitHub releases build it for Linux and Windows. Tiers and zone sets are append-only; the Manage view shows tier history in the map's log.
- Zone sets are published on the map's Manage view, `/maps/{map}/manage`, from a file or drawn in its 3D editor (or `sourcejump-api zones import <map> <file.json>`; `zones import-folder` seeds every map in a folder of such files that has no zones yet); both check the zone types, that tracks are shavit's (main and bonuses 1–8) with at most 128 zones, and that the main track has a start and an end, and both are logged.
- Run invalidation needs `invalidate_runs`: `POST /v1/staff/runs/{id}/invalidate` and `…/restore` for one run (from its page), `POST /v1/staff/invalidations` for every valid run of a `player` or `server` (across its keys), `GET …/invalidations/preview` to count them first, `GET /v1/staff/invalidations` (`?player=`, `?server=`) to list them and `POST …/{id}/restore` to undo one. Each takes a reason. `runs.invalidated_by` names the log entry that took a run, so an undo restores exactly that. Revoking a key with `invalidate_runs` also needs the privilege. `runs/invalidation.rs` recomputes the affected personal bests in the same transaction (ties keep the earlier run); every public read skips invalidated runs. Nobody invalidates or restores their own runs; restoring a server's invalidation leaves the restorer's own for a colleague.
- Bans need `manage_bans`: `GET /v1/staff/bans` (active, and the 50 latest ended), `POST /v1/staff/players/{player}/bans` (restrictions, reason, optional `ends_at`, `invalidate_runs` with `no_records`, which also needs that privilege), `POST …/bans/{id}/lift` (reason). `GET /v1/staff/players/{player}` answers any SteamID for staff with `manage_bans`, `invalidate_runs`, `manage_privileges` or `review_anticheat`, with bans only for the first. Restriction bits are in `players/restrictions.rs`; a player's restrictions are their active bans' (not lifted, not past `ends_at`: the `active_bans` view; `records_bans` are those with `no_records`). `bans` rows change only by one lift (trigger). Nobody bans themselves or lifts their own ban.
- `POST /v1/staff/players/{player}/privileges` (`grant`, `revoke`, reason) needs `manage_privileges`; the player page then lists what they hold. Only the changing half is logged, and a request that changes nothing is refused. Nobody changes their own, and `manage_privileges` itself changes only on the CLI.
- `GET /v1/staff/players/{player}/detections` needs `review_anticheat`: one player's anti-cheat detections (`staff/anticheat.rs`) for their Manage view, 50 a page, newest first by ID (a server's clock can be wrong), older via `?before=` (the page's `older`). Detections are read-only for now; what staff do with them is still open (`domain.md`). Reviewers may also read `GET /v1/staff/players/{player}`.
- Posts need `manage_posts`: `POST /v1/staff/posts/{id}/hide` removes someone else's post (reason; `posts.hidden_log_id` links the entry), `GET /v1/staff/posts` pages posts like `GET /v1/posts` with removed ones in place (with `removal`: who, when, why), `GET /v1/staff/posts/{id}` reads one even when removed, `POST …/{id}/restore` (reason) brings back one staff removed. An author's own removal can't be restored; nobody restores their own post. Community pages load removed posts, New post, Edit and Remove in the browser, so they render alike for all.
- Run comments take `manage_posts` too (`staff/run_comments.rs`), with the same rules: `GET /v1/staff/runs/{id}/comments` and `…/{comment}/replies` page them with removed ones in place, `POST /v1/staff/run-comments/{id}/hide` and `…/restore` take a reason (`run_comments.hidden_log_id` links the entry). The entries show in the run's and the author's logs.
- With `no_records`, the ingest stores a run invalid in the ban's log entry's name, answers `201` with no replay, and skips the map's `last_run_at`; it locks the player row shared and banning locks it exclusively, so a run racing a ban is caught either way. The player's Manage view lists them. `no_posting` refuses post and run comment writes; `no_profile_edits` refuses a player's own profile details. Lifting leaves invalidated runs out.
- Every staff action is written to `staff_log` in the transaction that makes it, from the web or the CLI (`staff/keys.rs`, `staff/servers.rs` hold the logged versions both use). The log is append-only (a trigger refuses changes); actions from the command line have no actor. `GET /v1/staff/log` lets any staff member read it, newest first, naming the player for actions on a player, paged by `?before=`/`?after=` (a page's `older`/`newer` entry IDs), filtered by `?kind=` (players, runs, servers, maps, rules, posts) and `?about=` (a SteamID in any form matches actor, target and a run's or post's player; anything else the target, or a server's ID or name in the detail); one run's, player's or map's at `GET /v1/staff/runs/{id}/log`, `…/players/{player}/log` and `…/maps/{map}/log`, 50 a page, older via `?before=` (the page's `older`).
